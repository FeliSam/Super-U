1) OBJECTIF DE CETTE APP (périmètre jusqu’aux appels)
================================================================================

Un coursier se connecte, voit les jobs de son magasin, rassemble le panier,
prend la livraison, envoie sa position GPS, parle et appelle le client
dans l’appli, livre (éventuellement encaisse COD), clôture.

Parcours cible bout-en-bout :

A. Login staff (email + mot de passe) → token Bearer ops.
B. Tableau de bord : 2 files
     - À rassembler (pick_jobs queued/assigned/picking)
     - À livrer (deliveries unassigned ou à moi)
C. Claim pick → start → cocher les lignes (picked_qty / unavailable / note) → pack.
D. Claim delivery → ouvre/attache une ops.courses (tournée).
E. Statuts livraison dans l’ordre :
     assigned → at_store → picked_up → en_route → arrived → delivered
     (ou failed + reason)
F. POST /ops/location pendant en_route (lng/lat/heading/speedMps).
G. Carte Cotonou (MapLibre) magasin → dropoff, overlay GPS coursier.
H. Chat fil courier-{orderId} (comms) avec le client de la commande.
I. Appel in-app (audio d’abord) : sonnerie, décrocher, muet, haut-parleur,
   clavier DTMF, attente, caméra simulée puis vraie, réduire, raccrocher.
   Persister l’appel dans comms.calls + bulle kind=call dans comms.messages.
J. Si WebRTC pas encore branché : MÊME UX que marche-dore (simulation visuelle)
   MAIS écrire quand même les lignes comms.* pour que le client les voie
   dès que son chat sera branché sur l’API (ne plus rester 100 % local).

2) MACHINES D’ÉTAT (respecter STRICTEMENT)
================================================================================

Boutique public.orders.status (ce que voit le client) :
  confirmed | preparing | shipping | delivered | cancelled

Picking ops.pick_jobs.status :
  queued → assigned → picking → packed
  + cancelled

Livraison ops.deliveries.status :
  unassigned | offered | assigned | at_store | picked_up
  | en_route | arrived | delivered | failed | cancelled

Tournée ops.courses.status :
  open | in_progress | completed | cancelled
  Une course ouverte/in_progress par coursier ; claim delivery s’y accroche.
  completed quand plus aucune delivery de la tournée n’est ouverte.

Mapping serveur (déjà en SQL) public.map_ops_to_shop_status(pick, del) :
  cancelled si pick ou del cancelled
  delivered si del = delivered
  shipping si del IN (en_route, arrived, picked_up)
  preparing si pick IN (picking, assigned, packed) OU del IN (assigned, at_store)
  sinon confirmed

Donc : packer sans claim delivery ⇒ client encore « préparation ».
Claim delivery + at_store ⇒ preparing.
picked_up / en_route ⇒ shipping + GPS visible client via GET /me/orders/:id/live.

Appels comms.calls.status :
  initiated → ringing → accepted → ended
  ou rejected | canceled | missed | failed

Un seul appel live par thread (index unique statuses initiated|ringing|accepted).

3) API DÉJÀ EXISTANTE (server/src/ops.ts) — UTILISER TELLE QUELLE
================================================================================

Base : EXPO_PUBLIC_API_URL (défaut http://localhost:8787)
Header : Authorization: Bearer <ops.staff_sessions.token>
JSON { ok: true|false, error? }

POST /ops/login
  body { email, password }
  → { token, staff: { id, email, phone, firstName, lastName, role, canPick, canDeliver, storeId, vehicle } }

GET /ops/me
  → { staff }

GET /ops/pick-jobs
  403 si !canPick
  → { jobs: rows de ops.v_pick_board }  (queued/assigned/picking du store)

POST /ops/pick-jobs/:id/claim     (id = pick-{orderId})
  queued → assigned, picker_id = moi
  409 si déjà pris

POST /ops/pick-jobs/:id/start
  assigned|picking → picking, started_at

PATCH /ops/pick-jobs/:id/lines
  body { lines: [{ productId, pickedQty?, unavailable?, note? }] }
  maj public.order_lines

POST /ops/pick-jobs/:id/pack
  picking|assigned → packed, packed_at
  event pick.packed

GET /ops/deliveries
  403 si !canDeliver
  board : unassigned OU courier_id = moi, même magasin
  colonnes v_delivery_board dont same_handler, cash_to_collect, coords, pick_status

POST /ops/deliveries/:id/claim     (id = del-{orderId})
  unassigned|offered → assigned
  crée/réutilise ops.courses in_progress
  trigger SQL : comms.ensure_courier_thread(order_id, courier_id)
  sync payload shop : courierName, courierPhone, managedBy ops

POST /ops/deliveries/:id/status
  body { status, reason?, proofUrl? }
  status ∈ at_store | picked_up | en_route | arrived | delivered | failed
  si delivered : clôture la course s’il n’y a plus de livraisons ouvertes

POST /ops/location
  body { lng, lat, heading?, speedMps? }
  upsert ops.courier_locations

GET /ops/orders/:id
  → { order: v_order_tracking, lines: order_lines, events }

Santé : GET /health

IDs :
  pick job  = pick-<orderId>
  delivery  = del-<orderId>
  thread    = courier-<orderId sans #>
  staff     = st-picker-* / st-courier-* (générés au seed)

4) API COMMS À AJOUTER AU SERVEUR (si absente — OBLIGATOIRE pour chat/appels)
================================================================================

Aujourd’hui comms.* existe en SQL + triggers, MAIS il n’y a PAS de routes HTTP.
Tu dois les ajouter dans server/ (nouveau fichier server/src/comms.ts
registerCommsRoutes) pour LES DEUX apps (token client OU token staff).

Auth mixte : essayer staff_sessions puis sessions client.
Marquer req.actor = { kind: 'customer'|'staff', userId?, staffId? }

Membres : un acteur ne lit/écrit un thread que s’il est dans comms.thread_members
(sauf dispatcher plus tard). Le trigger crée déjà customer + staff à l’assignation.

Routes minimales :

GET  /comms/inbox
  → threads de l’acteur (joindre comms.v_inbox + unread via last_read_at)

GET  /comms/threads/:id
  → thread + members (prénoms)

GET  /comms/threads/:id/messages?before=&limit=50
  → messages ordre chrono

POST /comms/threads/:id/messages
  body { kind: 'text'|'image', body, payload? }
  sender_kind / sender_*_id depuis le token

POST /comms/threads/:id/read
  last_read_at = now()

--- Appels ---

POST /comms/threads/:id/calls
  body { media: 'audio'|'video' }
  crée call status=initiated puis ringing
  caller = moi, callee = l’autre membre du fil (customer↔staff)
  409 si un appel live existe déjà sur le thread

POST /comms/calls/:id/accept     → accepted + answered_at
POST /comms/calls/:id/reject     → rejected
POST /comms/calls/:id/cancel     → canceled (si caller, pas encore accepted)
POST /comms/calls/:id/hangup     → ended | missed selon phase
GET  /comms/calls/:id
POST /comms/calls/:id/signals
  body { signalType: 'offer'|'answer'|'ice'|'hangup'|'reject', payload: object }
GET  /comms/calls/:id/signals?afterId=
  pour poll ICE/SDP (LISTEN pg_notify comms_signal en plus si tu peux)

POST /comms/devices
  body { platform, pushToken?, voipToken? }
  upsert appareil de l’acteur

Temps réel : polling 1–2 s des messages + call status suffit en V1.
Option : SSE ou WS plus tard. pg_notify canaux :
  comms_message, comms_call, comms_signal, marche_ops, marche_shop

Le trigger comms.notify_call INSERT déjà une bulle system kind=call
id = callmsg-{callId}-{status} — ne pas dupliquer côté client.

6) ÉCRANS — COMPORTEMENT DÉTAILLÉ
================================================================================

LOGIN
- Email / mot de passe, CTA « Entrer en course »
- Erreurs API en français
- Persister token (AsyncStorage / sqlite kv)
- Si canPick false : cacher file picking
- Si canDeliver false : cacher file livraisons
- Les comptes démo ont les deux à true

BOARD
- Section « Rassembler » : jobs queued (CTA Prendre) + mes assigned/picking
- Section « Livrer » : unassigned (CTA Prendre la course) + mes livraisons
- Carte job : n° commande, nb articles, créneau day_label/slot_label, total Fcfa,
  adresse courte, pastille same_handler « Vous rassemblez et livrez »
- COD : afficher cash_to_collect si > 0 (« Espèces à encaisser »)
- Pull-to-refresh + poll 4s

PICKING (job)
- Liste order_lines : name, unit, qty, stepper picked_qty, toggle rupture,
  note optionnelle
- CTA Commencer (start) puis Terminer le rassemblement (pack)
- Interdire pack si toutes les lignes unavailable sans note ? Non — autoriser
  mais marquer unavailable. Le client verra plus tard les substitutions (hors V1).

RUN (livraison)
- Carte MapLibre : pickup magasin, dropoff client, polyline si route_geojson
  existe sur l’order (payload routeCoordinates)
- Boutons d’étape (un à la fois, dans l’ordre) :
  Arrivé magasin → Colis récupéré → En route → Sur place → Livré
  + Échec (motif)
- Boutons Message et Appeler (in-app, pas tel:)
- Pendant En route : GPS toutes les 8s
- Livré : preuve photo optionnelle (proofUrl data/https) V1 peut skip
- COD : rappeler le montant avant Livré

CHAT
- Un fil par commande assignée (id courier-{orderId})
- Bulles moi = staff, eux = client
- Bulles appel (kind=call) avec icône phone + libellé FR
- Composer + envoi POST messages
- Header : téléphone → POST /comms/threads/:id/calls puis overlay

APPEL (UX à copier / améliorer depuis marche-dore)
Phases : idle | outgoing | incoming | active
Contrôles (visuels même en simu) :
  - Muet (micro coupé)
  - Haut-parleur
  - Clavier DTMF 0-9 * #
  - Attente (pause chrono)
  - Caméra (badge, media=video sur le call)
  - Réduire → bandeau flottant (revenir / raccrocher)
  - Raccrocher / Annuler / Refuser / Décrocher
Incoming : Refuser | Muet/Silence | Décrocher
Outgoing ~2s ringing puis connected si l’autre accepte ;
  si l’autre app n’est pas connectée : rester ringing jusqu’à cancel/missed (25s)
Persister statuses comms.calls. Le trigger écrit les bulles.

V1 WebRTC (si tu as le temps après l’UX) :
  caller POST call → POST signal offer
  callee poll signals → POST answer + ice
  media audio getUserMedia
Sinon : simulation visuelle + écriture DB, comme l’app boutique aujourd’hui.

- Pas de multi-tournée parallèle : une course in_progress
- Déconnexion : supprimer session locale (optionnel DELETE session serveur plus tard)
- Commande cancelled : jobs cancelled via trigger payload — retirer du board
- Fil comms créé SEULEMENT quand courier_id est set (claim delivery)
  Donc le chat picking-only n’existe pas en V1 (pas de thread tant que pas livreur)
