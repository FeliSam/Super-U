OBJECTIF SCHÉMA
---------------
public.orders reste le document boutique (payload JSON).
Des triggers extraient des colonnes indexables et UPSERT :
  ops.pick_jobs  (1 par commande)
  ops.deliveries (1 par commande)
Quand deliveries.courier_id est posé, trigger :
  comms.ensure_courier_thread(order_id, staff_id)
  → thread id = 'courier-' || replace(order_id, '#', '')
  → membres : customer (orders.user_id) + staff (courier_id)

Rôles DB (optionnels local) : marche_shop, marche_ops
  MDP local créés dans SQL : marche_shop_local / marche_ops_local
L’API Node actuelle se connecte souvent en superuser « marche ».

  status TEXT  chk confirmed|preparing|shipping|delivered|cancelled
  managed_by TEXT chk shop|ops

  dropoff_lng/lat, store_lng/lat
  route_distance_m, route_duration_s, route_profile, route_geojson JSONB
  created_at, updated_at

Payload JSON (champs lus par trg_orders_before) :
  status, storeId, storeName, itemCount, subtotal, delivery, discount, total,
  paymentId, paymentLabel, paymentStatus, paymentRef,
  dayLabel, slotLabel, addressLabel, addressLine, addressCity, addressPhone,
  comment,
  addressCoordinate [lng, lat],
  storeCoordinate [lng, lat],
  routeDistanceMeters, routeDurationSeconds, routeProfile, routeCoordinates,
  managedBy, lines[], courierName, courierPhone

public.order_lines PK (order_id, product_id)
  position, name, unit, qty, unit_price
  picked_qty, unavailable, note     -- écrits par l’app course

Trigger BEFORE INSERT/UPDATE OF payload : trg_orders_before (flatten)
Trigger AFTER  INSERT/UPDATE OF payload : trg_orders_after
  ensure_ops_jobs(NEW)
  ops.events order.created | order.updated
  pg_notify marche_ops, marche_shop

ensure_ops_jobs :
  sync order_lines depuis payload.lines
  cash_to_collect = total si payment_id='cod' OU payment_status='cod_pending'
  pick/del status init selon shop status SAUF si managed_by='ops'
    (alors on ne réécrit pas un job déjà avancé par le staff)
  ids : pick-{orderId}, del-{orderId}

map_ops_to_shop_status(pick, del) → status boutique (voir PROMPT-AGENT)

VUE public.v_order_tracking (client live + GET /ops/orders/:id)
  order + delivery_status, courier_id, courier_first/last/phone
  courier_lng/lat, courier_located_at
  pick_status, picker names, packed_at, same_handler
  same_handler := picker_id IS NOT NULL AND courier_id IS NOT NULL
                  AND picker_id = courier_id

COMMS — FILS / MESSAGES
================================================================================

comms.threads
  id PK
    support : 'support' (à créer à la main si besoin)
    courier : 'courier-' || orderId sans #
    order   : autre
  kind chk support|courier|order
  order_id FK NULL
  title, created_at, updated_at
  UNIQUE (order_id) WHERE kind='courier' AND order_id IS NOT NULL

comms.thread_members
  id BIGSERIAL
  thread_id FK
  actor_kind chk customer|staff|system
  user_id XOR staff_id selon actor_kind (CHECK)
  last_read_at, muted, joined_at
  UNIQUE (thread_id, user_id) where user_id not null
  UNIQUE (thread_id, staff_id) where staff_id not null

comms.messages
  id PK
  thread_id FK
  sender_kind chk customer|staff|system
  sender_user_id, sender_staff_id
  kind chk text|image|system|call
  body TEXT
  payload JSONB
    pour call : { call_id, status, media }  (écrit par trigger)
  created_at
  INDEX (thread_id, created_at DESC)

Trigger AFTER INSERT messages :
  touch threads.updated_at
  pg_notify comms_message { thread_id, message_id, kind }

VUE comms.v_inbox : thread + last message

COMMS — APPELS (jusqu’au WebRTC)
================================================================================

comms.calls
  id PK  (générer call-{uuid} côté API)
  thread_id FK NOT NULL
  order_id FK NULL
  caller_kind chk customer|staff
  caller_user_id / caller_staff_id  (CHECK selon kind)
  callee_kind chk customer|staff
  callee_user_id / callee_staff_id
  media chk audio|video DEFAULT audio
  status chk
    initiated|ringing|accepted|rejected|canceled|missed|ended|failed
  end_reason TEXT
  started_at, ringing_at, answered_at, ended_at

  UNIQUE PARTIEL : un seul live par thread_id
    WHERE status IN (initiated, ringing, accepted)

Trigger AFTER INSERT OR UPDATE OF status :
  pg_notify comms_call { call_id, thread_id, status }
  INSERT message kind=call id='callmsg-'||id||'-'||status  (ON CONFLICT DO NOTHING)
  body FR :
    initiated → Appel en cours
    ringing → Sonnerie
    accepted → Appel accepté
    rejected → Appel refusé
    canceled → Appel annulé
    missed → Appel manqué
    ended → Appel terminé
    else → Appel

MACHINE D’APPEL (côté API à implémenter, pas encore de routes) :

  POST create
    INSERT initiated, puis UPDATE ringing + ringing_at
    caller = token, callee = l’autre membre du fil
    409 si unique live violé

  accept (callee) : ringing → accepted, answered_at=now()
  reject (callee) : ringing|initiated → rejected, ended_at
  cancel (caller, pas encore accepted) → canceled
  timeout client ~25s sans accept → missed
  hangup (accepted) → ended, end_reason optionnel
  failed si signalisation casse

Durée affichée = ended_at - answered_at

comms.call_signals  (SDP / ICE)
  id BIGSERIAL
  call_id FK
  sender_kind customer|staff
  sender_user_id / sender_staff_id
  signal_type chk offer|answer|ice|hangup|reject
  payload JSONB   -- { sdp } ou { candidate, sdpMid, sdpMLineIndex }
  created_at
  INDEX (call_id, id)
  Trigger INSERT → pg_notify comms_signal { call_id, signal_id, type }

Flux WebRTC V1 (polling GET signals?afterId=) :
  1. A crée call
  2. A getUserMedia → RTCPeerConnection → createOffer → POST signal offer
  3. B poll call ringing + signals offer → setRemoteDescription
     createAnswer → POST answer + ice
  4. A ice trickle POST ice ; B aussi
  5. hangup → POST signal hangup + PATCH call ended
  Simulation sans média : skip 2–4, garder 1 et 5 + UI contrôles
  (muet, HP, DTMF local, hold, video flag media=video, minimize)

INVARIANTS À NE PAS CASSER
================================================================================

- 1 pick_job par order, 1 delivery par order
- picker_id et courier_id PEUVENT être égaux (coursier solo)
- managed_by='ops' empêche ensure_ops_jobs d’écraser un statut staff
  quand le client resauvegarde son payload
- Thread courier créé seulement si courier_id NOT NULL
- Pas deux appels live sur le même thread
- Messages call générés par trigger : id déterministe callmsg-{id}-{status}
- L’app course n’update PAS orders.status directement :
  elle update pick_jobs/deliveries puis l’API syncShopFromOps
  (patch payload.status via map_ops_to_shop_status + courierName/Phone)
